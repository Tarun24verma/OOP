Polymorphism

One instruction, many forms. Understanding it through a real checkout() example.

DefinitionWhat is Polymorphism?

Polymorphism is the ability of different objects to respond to the same method call in their own way.
From Greek: poly = many, morph = forms  →  "many forms"
  • The caller uses one common interface (a method name like pay())
  • Each object decides what that method actually does

Real lifeThe "Please pay" moment

A cashier says the same thing every time: "Please pay." What happens next depends on how you pay.

💵

Cash

Hand over notes, get change back

📱

UPI

Scan the QR code, enter your PIN

💳

Card

Swipe or tap, then confirm

🏦

Net banking

Log in and approve the transfer

The cashier doesn't care about the details. One action, many forms.

Types in PythonWays polymorphism shows up

Method overriding

A child class redefines a method of its parent. The right version runs at runtime.

Duck typing

No shared parent needed. If an object has the method, it works.

Built-in functions

len() works on strings, lists, dicts and more.

Operator overloading

+ adds numbers, joins strings, merges lists. Your classes can define it too via __add__.

Python has no method overloading by signature. A later def with the same name replaces the earlier one.

Common thread: a family of types, one shared method name, different behaviour.

Example · Part 1checkout(): the payment classes

class Payment:
    def pay(self, amount):
        raise NotImplementedError

class Cash(Payment):
    def pay(self, amount):
        return f"Handed over ₹{amount} in cash"

class UPI(Payment):
    def pay(self, amount):
        return f"Scanned QR and paid ₹{amount} via UPI"

class CreditCard(Payment):
    def pay(self, amount):
        return f"Swiped card and paid ₹{amount}"
Payment defines the common method name. Each subclass overrides pay() with its own behaviour.

Example · Part 2checkout(): the cashier function

def checkout(method, amount):
    print(method.pay(amount))     # cashier just says "pay"

checkout(Cash(), 500)
checkout(UPI(), 500)
checkout(CreditCard(), 500)
Output
Handed over ₹500 in cash
Scanned QR and paid ₹500 via UPI
Swiped card and paid ₹500
checkout() never checks the type. It just calls method.pay().

Under the hoodHow Python picks the right pay()

checkout(method, 500)
→
method.pay(500)
resolved at runtime
→
Cash.pay() if method is Cash
UPI.pay() if method is UPI
CreditCard.pay() if method is CreditCard
Python looks at the actual object's class (and its MRO) when the call happens,
then runs that class's version of pay().

Try itSame call, different behaviour

>>> checkout(Cash(), 500)
Handed over ₹500 in cash

Click a payment method. The line checkout(...) stays the same; only the object changes.

ExtensibilityAdd a new method. checkout() stays untouched.

class Wallet(Payment):            # new class, added later
    def pay(self, amount):
        return f"Paid ₹{amount} from wallet balance"

checkout(Wallet(), 500)           # works immediately
Output
Paid ₹500 from wallet balance

Changed: one new class

Not changed: checkout(), Cash, UPI, CreditCard

Why it mattersWithout vs with polymorphism

✗ Without: type-checking chain
def checkout(kind, amount):
    if kind == "cash":
        print(f"Handed over ₹{amount}")
    elif kind == "upi":
        print(f"Paid ₹{amount} via UPI")
    elif kind == "card":
        print(f"Paid ₹{amount} by card")
    # new method? edit this
    # function every time
✓ With: one method call
def checkout(method, amount):
    print(method.pay(amount))


# new method? just write a
# new class with pay().
# checkout() never changes.
  • Less repetition, no long if/elif chains
  • Easy to extend without touching working code

SummaryKey takeaways

  • Polymorphism = same method name, different behaviour depending on the object
  • In Python it comes from overriding, duck typing and special methods like __add__
  • The caller (checkout()) depends only on the common interface, not the concrete type
  • New types can be added without modifying existing code
Give the same instruction to different objects, and trust each one to do the right thing in its own way.
